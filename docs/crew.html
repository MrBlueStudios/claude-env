I'm turning my Claude Code environment into something all four of us run — the same tools, the same guardrails, the same shared knowledge, installed with one line in your NixOS config. Here's what it is, what you get, and the two things left to do.

The original four asks, for reference
  1. Your SSH public key Run cat ~/.ssh/id_ed25519.pub — if that errors, make one with ssh-keygen -t ed25519 first. Send the whole single line, starting ssh-ed25519. This is a public key, safe to paste. If anything you send starts with -----BEGIN OPENSSH PRIVATE KEY-----, stop — that's the wrong one.
  2. Your GitHub username So I can add you to the repos.
  3. The email on your Jira account So you land on our shared board. This is the one everyone forgets.
  4. Your hardware Run fastfetch, then nvidia-smi --query-gpu=name,memory.total --format=csv. If the second one prints nothing useful, that's a fine answer — it means no NVIDIA card. I need this to work out who can host the shared ranking model, who can run local models, and whether Roblox Studio under Wine is realistic on your machine.

How it gets to your laptop

It isn't a folder of dotfiles you copy and then slowly drift away from. It's a flake. You add one input and one import to your own NixOS config, rebuild, and you have the whole environment. When I improve something, you run nix flake update and you have it too.

The walkthrough

Six steps, about twenty minutes, most of it the rebuild. Every command below runs in the directory that holds your own flake.nix — for most NixOS installs that's /etc/nixos; if you keep your config in a repo under your home directory, it's that directory instead. Steps 1 and 6 are the ones that catch problems, so don't skip them.

Before step 2 can work — this one is mine, not yours

claude-env is public, but it pulls in one private repo of mine for the web-design playbook. Until I've given your GitHub account read access to that repo, step 2 fails for all three of you with a permission error on git@github.com — and it fails at lock time, before anything is built, so the error won't look like it has anything to do with the playbook. If you hit that, stop and tell me; it's not your SSH setup.

  1. Check what you're starting from 
    nixos-version
claude --version

    You want 26.05 (all three of you are) and Claude Code 2.1.324 or newer. Below that floor, the plugin marketplace pins are ignored and you silently get whatever is on their main branches instead of the versions I tested — Claude Code itself keeps working, which is why it's worth checking now rather than wondering later. If claude isn't found at all, that's expected: it comes from nixpkgs, and the flake configures it rather than installing it. Add claude-code to your packages, rebuild once, and sign in.

    Done when both commands print a version and the Claude one is ≥ 2.1.324
  2. Add the input

    In the inputs block of your own flake.nix:

    inputs.claude-env.url = "github:MrBlueStudios/claude-env";

    No follows line is needed. The flake deliberately declares no nixpkgs of its own — you bring yours, so nothing here can drag a second copy of nixpkgs into your closure.

    Done when nix flake metadata lists claude-env without erroring
  3. Import both modules

    There are two, and you need both: the home-manager one is the tools, the NixOS one is the brakes. Replace <you> with whatever whoami prints.

    # in your NixOS configuration
imports = [ inputs.claude-env.nixosModules.default ];

home-manager.users.<you>.imports = [
  inputs.claude-env.homeManagerModules.default
];

claude-env.tier = "blitsol";   # "base" is the default

    All three of you are on the Blitsol tier, so all three of you set that line. Leave it out and you get the base tier, which is everything except Blitsol's own accounts and secrets.

    Done when nix flake check — or just the next step — gets past evaluation
  4. Rebuild 
    sudo nixos-rebuild switch --flake .#$(hostname)

    Or nh os switch . if you have nh, which is what I use. The first build is the slow one: it fetches the MCP servers and the plugin pins. A second run takes seconds.

    Done when the switch completes and prints a generation number
  5. Verify, in any directory 
    claude mcp list
claude plugin list
claude-plugins-check
ls ~/.claude/skills

    The first two should list servers and plugins; claude-plugins-check is mine and tells you whether every marketplace pin actually applied — that's the one that catches a half-finished install. The last one should print a directory full of skills rather than nothing.

    Done when claude-plugins-check reports no unpinned marketplace
  6. Write down everything that went wrong, and send it to me

    Including the parts you worked out yourself. This is the actual point of one of you installing it while I don't help: every rough edge you hit, the next person hits too, and the only way it gets fixed is if I know about it. The error text matters more than your description of it — paste it.

    Done when I have your notes, even if the notes say "it just worked"

After that, keeping up with it is one command, in the same directory: nix flake update claude-env then the same rebuild. You stay on the version you updated to until you choose to move.

The guardrails, so nothing surprises you

Claude Code in this setup runs behind a guard that sits above project settings — meaning a repo you clone cannot switch it off. It will refuse some things. That's deliberate, and it's the part I most want you to have, because we're going to point these agents at client sites and real money.

What it refuses outright:

reading any .env /run/agenix/** ~/.ssh/id_* destructive shell commands

If it blocks something you genuinely need

Don't fight it and don't let Claude find a way around it — that's the one behaviour that makes a guard worthless. Tell me, and I'll either widen the rule or tell you why it's there.

The shared memory — the part I'm most excited about

Jira and GitHub record what we did. They don't record what we tried, what we want to build, or where we're stuck — and that's exactly the knowledge that disappears. Kish burns two days on an approach Almar already found was a dead end, and nothing in either tool would have said so.

So: a shared Obsidian vault that each of our Claudes can read. Four separate stores, because these things rot at completely different speeds and lying to you confidently is worse than telling you nothing.

And the questionnaire — this is the part I'm handing you now

Five sections: current projects, ideas you haven't started, what you've built that someone else could reuse, what you tried and dropped, and what you want to get better at. Fifteen minutes is the budget; if a section runs long, answer less of it rather than skipping the next one — three thin projects beat one perfect one and three blanks.

You need nothing installed to answer it. That's worth saying plainly, because the install walkthrough above might make it look otherwise. The vault lives on one laptop today, and I paste your answers into my Claude, which writes the notes with owner set to you, never to me. Plain prose is the right format — a chat message, a text file, a voice note. The blocks in the questionnaire are a shape to answer along, not something you have to produce.

The section I most expect you to skip is the second one, ideas you haven't started, because nothing has started yet so it feels like it doesn't count. It's the section the whole duplicate-check runs on. List the ideas you'd be annoyed to find someone else had already half-built, including the ones you think are a bit silly: writing one down costs a line, and two people discovering the overlap in month three costs a fortnight.

  2. You answer the questionnaire. Nothing to install, fifteen minutes, and it's the thing that decides whether the shared memory is useful on day one or empty.
