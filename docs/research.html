How to run one

  1. Open the item, copy the whole prompt. It already carries the context and the output format — add nothing.
  2. Paste it into your Claude. If it can search the web, good. If it can't, it should say what it could not check rather than guess.
  3. Insist on the format. Question, three-sentence answer, confidence, what would change our decision, numbered findings with sources, a "not checked" list. That shape is what lets sixteen answers from four people get merged without re-reading sixteen essays.
  4. Save it as <slug>.md and send it to Léon. Once the repo exists, it lands in research/ and the item gets ticked.

Anything your Claude marks UNVERIFIED is more useful than something it states confidently and wrongly. Ask it to be honest about what it couldn't reach.

nixos-version-matrix

Léon answered

Decides whether the flake can ship one module for everyone, and whether Léon upgrades.

Found by: the inventory. Léon is on NixOS 25.05, Ryan and Kish on 26.05.

Yes, and it was tested rather than read: Léon's actual Claude home-manager module and the guard NixOS module were evaluated against both releases. The NixOS module passes on both unchanged; the home-manager module passes on 25.05 and fails on 26.05 on exactly one line (`pkgs.nodePackages.prettier`, removed in nixpkgs 26.05), and the fix must be release-guarded because `pkgs.prettier` does not exist on 25.05. The shared flake should expose modules only and never pin home-manager; Léon's own upgrade is a branch bump for three inputs plus two package-attribute fixes, with `stateVersion` left alone — and it is overdue, because the 25.05 branch he is on stopped receiving updates at the end of 2025.

Confidence high for module compatibility (evaluated, not inferred); medium for the upgrade cost (only the Claude modules were evaluated on 26.05, not the whole system).

What would change the decision

  • A full-system evaluation of `/etc/nixos` on 26.05 (command in finding 9) showing breakage in stylix, nixvim or the AGS widgets beyond a branch bump. Then Léon stays on 25.05 a little longer and the flake simply keeps supporting both, which it must anyway.
  • an or Kish moving to nixos-unstable. Then the guard becomes "25.05 or newer", not "25.05 or 26.05".

desktop-neutral-module

Kish answered

Decides which parts of Léon's config must be stripped or guarded before the module ships.

Found by: the inventory. Two of four run KDE Plasma on Wayland, Léon runs Hyprland.

`notify-send` itself should work on Plasma with no extra configuration; the things that break are the ones that leak Léon's desktop into the module. The one serious risk is any `xdg.portal` or `wayland.windowManager.hyprland` setting on the home-manager side, which hides the KDE portals that NixOS installs. The smaller risks are `wl-copy` (not present by default on KDE, and version-sensitive on KWin), a Kitty-only notification channel in shared settings, and `notify-send` flags that block a hook.

Confidence medium — the portal and clipboard findings rest on issue trackers and docs, and nothing here was tested on real Plasma hardware.

What would change the decision

  • If Léon's module does not touch `xdg.portal`, Hyprland options, the clipboard, or `preferredNotifChannel`, almost nothing needs stripping and the checklist below becomes a five-minute grep.
  • NixOS 26.05 ships `wl-clipboard` older than 2.3.0, clipboard *watching* (`wl-paste --watch`) cannot work on Plasma and any tool using it needs a guard or a different mechanism.

Full write-up with sources: research/desktop-neutral-module.md in the claude-env repo.

flake-pinning-strategy

Ryan answered

Decides how four laptops stay on one revision without drifting, and whether a shared cache is worth it.

Point every consumer at a `stable` branch (or tags) of `claude-env` and let each laptop's own `flake.lock` do the pinning; the maintainer moves `stable` only when a revision is ready, and "update now" is simply that branch moving. Do not set up a binary cache yet: a modules-only flake is evaluated against each person's own nixpkgs, so there is almost nothing identical to share, and nearly everything already comes from the official cache. Detecting "I am behind" is a two-line comparison of the locked revision against the branch head, which belongs in the status line the module already ships.

Confidence medium — lock-file behaviour and Cachix's limits are documented; the claim that a cache would rarely hit is reasoning about how modules are built, not a measurement.

What would change the decision

  • If the flake starts shipping something heavy that is built from source (the Roblox toolchain, `contrastive-lm`, a patched package), a cache becomes worth it — but only if all four also share one nixpkgs revision.
  • `claude-env` is a private repository, both the input URL and the cache choice change (finding 7).

Full write-up with sources: research/flake-pinning-strategy.md in the claude-env repo.

agenix-multi-recipient

Léon answered

Decides the shape of the enrolment runbook, and whether revocation really revokes.

Adding a recipient is one edit to the rules file plus `agenix -r`, run by anyone holding a private key that is in the *current* ciphertext's recipient list; every listed `.age` file is decrypted and re-encrypted, there is no per-file shortcut. Removing a recipient the same way only stops them opening *future* ciphertext; anyone who pulled the repo before can decrypt the old files forever, so a departure means rotating the secret values at the provider. Bad keys fail loudly before anything is written, but a rekey that fails mid-list leaves earlier files re-keyed and later files not, so the runbook must check the exit code.

Confidence high — every claim below was reproduced in a throwaway repo with agenix 0.15.0 and age 1.2.1, the exact versions on Léon's machine.

What would change the decision

  • Wanting per-person revocation *without* rotating the secrets. No file-based scheme can do that; it would need a server that checks identity on every read (a self-hosted Vaultwarden, or the providers' own team features), which is a different design.
  • iends keeping their SSH private key behind a passphrase or hardware token. age prompts for the passphrase; hardware keys need `age-plugin-*`. Neither was tested here.

Full write-up with sources: research/agenix-multi-recipient.md in the claude-env repo.

clm-hosting-reality

Léon answered

Decides whether CLM exists in this environment at all.

Found by: the inventory. CLM-8B's bf16 encoder needs ~16 GB VRAM (clm-mcp-server README).

The largest GPU in the crew is Ryan's 6 GB. Léon has a spare laptop or PC, unconfirmed.

The bf16 path needs a 24 GB NVIDIA card: the Qwen3-8B weights alone are 16.4 GB, more than any 16 GB card can hold once vLLM reserves memory for its cache. A Q4_K_M GGUF with full offload needs about 5.5 GB, so an 8 GB card is comfortable and Ryan's 6 GB RTX 2060 is borderline — but nobody has measured how much ranking quality CLM's heads lose on quantised embeddings, which is the real unknown. Léon's own Arc 140T was benchmarked: 64 tokens/s of prompt processing via Vulkan, three times the CPU, but only after disabling fp16 shaders because the Mesa 25.0.7 driver that ships with NixOS 25.05 hangs the GPU; the spare machine could not be checked from here because it is not on the tailnet.

Confidence medium — the VRAM arithmetic and the iGPU numbers are measured or derived from official file sizes; the quality of CLM on Q4 embeddings is unmeasured, and the iGPU result may change a lot with the newer Mesa in 26.05.

What would change the decision

  • A measured comparison of CLM's rankings on bf16 versus Q4_K_M embeddings over ~50 real idea pairs. If Q4 holds up, Ryan's 2060 or Léon's laptop can host it and the spare box is unnecessary; this belongs with Ryan's `dedup-without-clm` item.
  • e spare machine turning out to have an NVIDIA card with 8 GB or more.
  • e Arc 140T numbers after Léon's 26.05 upgrade (Mesa 25.0.7 → 25.3 or newer). If prompt processing lands near the 140V's reported ~490 t/s, the laptop becomes the obvious host.

Full write-up with sources: research/clm-hosting-reality.md in the claude-env repo.

dedup-without-clm

Ryan answered

Decides whether idea-collision detection needs CLM at all, or a small embedding model does it.

New. At four people and perhaps a few hundred recorded ideas, ranking by cosine similarity

with a small sentence-embedding model may be enough — and runs on every laptop's CPU.

B now, A later only if B visibly misses things: a small embedding model ranks a few hundred paragraphs on any laptop CPU in well under a second, and the existing calibrated yes/no check covers the precision the small model lacks. On similarity-style benchmarks the small models sit within a few points of the 8B class; the large gap is on hard retrieval, which is not this task. Start with `bge-small-en-v1.5` (MIT) if ideas are written in English.

Confidence medium — model sizes, licences and benchmark scores are from papers and model cards; no published benchmark matches "near-duplicate project ideas at n ≈ 500", and no latency was measured on our hardware.

What would change the decision

  • If a hand-made test set of 20–30 known overlapping idea pairs shows B ranking the true match outside the top 3 more than occasionally, move to a mid-size model first (finding 7), and to A only after that.
  • ideas are written in Dutch or mixed languages, the English-only models are the wrong pick (finding 8).

trading-free-data

unassigned — whoever drives the trading bot answered

For crypto, exchange public APIs are the only genuinely free live source: Binance's REST and WebSocket need no account for market data, allow 1,200 requests a minute, and go back years; use CCXT (MIT) so the exchange can change. For aggregated or cross-exchange data, CoinGecko's Demo key gives 10,000 calls a month with a year of hourly history, REST only. For US stocks, Alpaca's Basic plan is free with IEX-only quotes, 200 requests a minute, 30 streamed symbols, history since 2016 and the latest 15 minutes withheld; yfinance works for research but should not be in the loop of a running bot.

Confidence medium — Alpaca's and CoinGecko's limits are from their own pages; Binance's are from secondary comparisons and should be read off Binance's API documentation before the bot depends on them.

What would change the decision

  • A bot that polls every minute: one such bot alone uses about 43,000 calls a month, so any monthly-capped API (CoinGecko Demo, Twelve Data) is out and only exchange streams or Alpaca's uncapped plan fit.
  • ading non-US stocks or needing the consolidated tape: Alpaca's free tier does not cover it, and every stock alternative found costs from about $9 a month.

obsidian-multi-person-sync

Kish answered

Decides the foundation of the memory system. Everything else sits on this.

Use a git-backed vault (option A) — it is the only one of the three that actually merges two people's edits to the same note instead of producing duplicate files or risking loss. It only holds up if Claude Code hooks write one file per session rather than appending to a shared note, and if the hook does its own commit and push instead of relying on the Obsidian plugin. Syncthing is a workable second choice with whole-file conflict copies; Taildrive is alpha and should be ruled out.

Confidence medium — the conflict behaviour of git and Syncthing is from their official documentation, but the obsidian-git plugin's exact behaviour on conflict and the hook interaction are reasoned from partial sources and not tested.

What would change the decision

  • If people regularly edit the *same note at the same time* (live co-writing, not just overlapping within a few minutes), git's merge markers become a daily chore and a real-time tool is needed instead — not evaluated here.
  • the memory design ends up needing shared notes that many sessions append to, the "one file per session" rule fails and the append-only notes need the `merge=union` setting described in finding 5, with its ordering caveat.

Full write-up with sources: research/obsidian-multi-person-sync.md in the claude-env repo.

memory-schema-prior-art

Claude, in Léon's environment answered

The published schemas agree on three things we should copy: frontmatter is the schema and a hook lints it on every write; one durable fact per file, superseded by linking rather than editing; and an always-loaded index under a few hundred lines that points at files loaded on demand. None of them has a first-class "attempt" or "dead end" type, so the four-store split is an extension of prior art, not a contradiction of it; the closest ancestors are MADR's `rejected` and `superseded by` statuses and obsidian-mind's `confidence` field. Below is a concrete schema per store and a query rule that never loads the whole vault.

Confidence medium — the prior art is read from the projects' own READMEs and templates, but no schema was tested against real sessions; the field proposals are design, not findings.

What would change the decision

  • If a session-end hook cannot reliably fill `outcome` and `components` without a human, the Attempts store degrades into a log nobody queries; a two-week trial decides this.
  • the MCP memory server's graph (entities, relations, observations) turns out to be what people actually query, the four stores should be mirrored into it rather than replaced by it; today the graph lives per machine and is being pruned for that reason.

Full write-up with sources: research/memory-schema-prior-art.md in the claude-env repo.

memory-dashboard-options

Almar answered

For the first month use Obsidian Bases inside the vault (option A): it is built in, free, needs no code, and can edit a note's status from the table. Later, if people want it outside Obsidian or want computed things Bases cannot do, build the small SvelteKit app that reads a local clone of the vault (option B). A hosted page (option C) is the weakest fit: free hosting is easy, but keeping it private, current and writable is not.

Confidence medium — Bases' capabilities are from Obsidian's own help pages; the SvelteKit and hosted options are reasoned from how the pieces work, not from a build.

What would change the decision

  • If "idea overlaps" is the view people care about most, Bases cannot produce it (it only filters and sorts properties) and option B moves up — it depends on the outcome of `dedup-without-clm`.
  • the vault does *not* end up on every laptop (that is, if the sync decision is not git or Syncthing), option A stops working for anyone who does not hold the files.
